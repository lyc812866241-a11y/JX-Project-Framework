# AGENTS.md 通用协作与执行框架

> 维护版本：2026-09-10-r6。新增 K12 执行验证合同与执行包路由；保留 r4 的治理机制。历史：r4 新增 K11/W05 项目维护与继承验收，覆盖记录、结构、环境配置及机制自身的维护；历史项目须显式核对后迁移。

> 适用范围：AI 辅助的软件开发、学习与观念迭代等项目。软件专属条款仅用于涉及软件的项目；按实际任务填写目标、资料、流程和验证方式。
>
> 使用方式：将文中的 `<占位符>` 替换为项目实际内容；删除不适用的可选条款。项目特有的业务规则、字段定义、环境信息和操作手册应放入专门文件，不应堆积在本文件中。

## 自动生成项目专用框架

本节规定如何使用下文通用条款；先按项目需要裁剪，再执行保留的条款，不直接套用全部章节和目录。

**触发条件**：用户要求在一个明确的具体项目中使用本框架时，自动执行以下流程；仅阅读、讨论或维护本框架时不创建项目文件。项目目录不明确时，先确认目标目录。

1. **了解项目**：读取项目已有 `AGENTS.md` 及必要资料，识别目标、技术栈、当前任务和验证方式。保留已有有效约定与用户工作。
2. **选择工作流**：读取本框架所在目录的 `工作流库/README.md`，实际读取并纳入全部基础必选工作流（项目初始化、系统建模、验证收尾、发布回滚、项目维护）；再根据当前需求选择并读取可选工作流（如 UI 设计）。基础必选必须保留规则与触发条件，按项目类型适配；未触发时不执行、不创建空文件，无适用场景时注明原因。可选流程没有匹配项则跳过，不虚构库中内容。库或必选文件无法访问时报告初始化未完成项，不静默跳过。
3. **生成专用框架**：先按下方核心机制清单建立来源到目标条款的映射，再在项目根目录创建或按需更新 `AGENTS.md`。写入项目事实、适用原则及工作流的触发条件、行为和验证；领域内容可改写，核心机制不得静默删除。短流程直接写入；较长流程放入必要的专用文件并从 `AGENTS.md` 路由。
4. **创建文件并填写**：仅创建所选流程当前确实需要的文件；将占位符替换为已确认的项目内容。未知项标记“待确认”，关键未知先询问，不编造业务规则、命令或环境。下文推荐目录和检查表是按需选项，不要求批量建齐，也不创建空壳文档。
   - 按 W05 建立本项目的“维护登记表”：记录角色到实际路径/章节、唯一职责、读取/更新触发、写入所有者、验证及证据的映射。角色可合并到已有文件，但不能省略当前状态、历史恢复、结构导航和维护流程；环境与外部接口按条件适用，标明重新启用条件。未绑定的必需角色记未完成，不得仅留下模板路径。
5. **初始化 Git（默认必做）**：检查项目是否已处于 Git 仓库中（包括上级仓库和 worktree）；已有仓库则沿用，保留历史与未提交改动，不创建嵌套仓库。尚无仓库时，在项目根目录执行 `git init`。按实际技术栈创建或补充 `.gitignore`，排除本地密钥、依赖目录、构建产物和临时文件，保留已有有效规则。通过 `git status` 检查结果，并将仓库位置及适用的 Git 约定写入项目 `AGENTS.md`。Git 不可用时报告未完成项，不擅自安装或修改全局配置。本步骤不自动提交、创建远程仓库或推送。
6. **检查结果**：逐项核对核心机制映射及必选工作流，实际读取目标条款，检查触发、行为、边界和完成证据，而非只查标题关键词。用正常与反例场景检查至少自然语言转规格、范围变更、根因修复、交接恢复；遗漏项、失效链接或不成立的裁剪理由不得标为迁移完成。同时检查文件引用、项目事实及适用的 Git 初始化结果。报告通过、未通过、待验证及采用的源版本。
   - 必须执行 W05 的领域适配场景审阅：状态变化、文件/职责变化、外部 API 或输入变化、维护规则升级。检查实际绑定及步骤，并尝试遗漏维护者、保留冲突的当前状态、断开本地流程引用等反例。只有 ID 或通用库链接不算继承完成；未做真实运行时只报告文档验收通过。

用户要求将本框架应用到项目，即授权上述本地初始化步骤，无需再次审批；Git 初始化规则应保留在项目专用框架中。后续业务变更仍遵循项目约定。

**选用原则**：基础必选保留，按需流程以用户当前目标和项目已有规则为依据选择。工作流与其冲突时不自动覆盖；需要关键取舍时询问用户。初始化文件不代表获得部署或其他外部操作的授权。

**来源与更新**：在项目专用文件中简短记录所选工作流的源文件位置及适用原因。项目使用填好内容的本地版本，不依赖每次读取原始库；库更新后按需比较，不自动覆盖项目规则。重复读取本框架时只补必要差异，不重复生成文件。

## 1. 最小启动与按需路由

任何工作窗口开始时，按顺序读取以下最小事实集：

1. `<项目控制目录>/INDEX.md`：权威文档索引与读取路由。
2. `<项目控制目录>/CURRENT_TASK.<json|yaml|md>`：当前任务、阶段、状态和下一门禁。
3. `<基线目录>/current-baseline.<json|yaml|md>`：当前源码、构建或运行基线。

随后根据本轮实际动作按需续读，不得为保险而无差别加载全部项目资料。当前任务中的上下文清单（如 `required_context`）只是续读候选，只读取影响本轮判断、修改或验证的条目。普通链接不代表内容已加载；被路由到的文件必须实际读取。

| 本轮动作 | 必须续读的资料类型 |
|---|---|
| 讨论需求、形成方案或任务规格 | 需求基线、当前任务记录；涉及协作时读取角色与节点规则 |
| 编码、修复缺陷、热修复 | 开发模式、环境说明、当前任务记录、相关代码与局部规范 |
| 测试、工程验证、部署或回滚 | 工作流、环境说明、当前任务记录、部署与回滚资料 |
| 查看全局进度、同步或归档 | 项目状态；发生写入时再读取归档工作流 |
| 角色分工、创建执行节点或跨窗口协作 | 节点职责；需要合同细节时再读取角色定义 |
| 涉及端口、服务、凭证引用或外部接口 | 环境说明及任务指定的接口资料 |
| 架构审计或需求—代码一致性检查 | 需求、架构、工作流及相关代码映射 |
| 计划/文件/接口/配置/规则变化、任务暂停或交接 | 本地维护登记表及命中变化类型的维护步骤、对应事实源 |

采取动作前，至少确认：

- 当前任务编号、目标、依据和阶段；
- 当前状态所有者与允许写集；
- 当前源码或运行基线；
- 已知首错、下一门禁和停止条件；
- 与本轮动作直接相关的安全及业务约束。

## 2. 机器可读合同优先

- 对字段、状态、接口、权限、枚举和校验规则存在机器可读合同时，该合同是唯一结构化事实源。
- Prompt、流程图、应用层校验、测试、文档和展示必须与机器合同一致，不得各自维护相互独立的规则副本。
- 业务专属字段及条件规则应登记在 `<项目控制目录>/contracts/` 或 `<项目控制目录>/architecture/`，由本文件提供路由，不在本文件中逐项展开。
- 自然语言语义判断与确定性结构校验应明确分工。结构校验负责类型、枚举、作用域、状态、权限、版本和幂等等可验证约束；不得暗中加入未经登记的语义推断。
- 修改合同必须包含版本策略、兼容性判断、受影响消费者、迁移方式和回滚方式。

## 3. 指令转 Task Spec 与变更门禁

### 3.1 非讨论类指令必须先转为 Task Spec

- 凡用户要求执行动作或产出可验收结果，包括开发、修复、修改文档、调查、评审、测试、整理和部署，AI 必须先将自然语言指令整理为包含下列五项的 Task Spec，再执行对应工作。用户不必自行填写模板。
- 仅解释概念、交换观点、探索可能性，且没有要求执行或交付的纯讨论，不强制生成 Task Spec。“可以帮我做……吗”应按实际执行意图识别，不得仅当作能力询问。混合请求只对执行部分形成规格。
- 先从用户原话、已确认决策和实际读取的相关资料中提取内容；不得擅自增加目标、扩大范围、改变业务规则，或把 AI 推测写成用户要求。
- 缺少资料时，先形成简短草案，可直接开展必要的只读调查以补齐上下文；只读调查本身也应说明五项内容，但不因此新增变更审批。
- 简单任务可在当前回复中用五项简短文字表达；需持久追踪或涉及项目/外部状态变更的任务，应按项目约定登记到 `<项目控制目录>/tasks/`。已有 Task Spec 时补充当前任务，不为同一任务重复建立相互独立的规格。

### 3.1a 自然语言转换与协作补全（2026-09-10）

- 用户负责表达期望结果和关键取舍，AI 负责整理专业执行规格；不得要求用户先提供完整技术术语、命令或字段才能开始工作。
- 先识别本轮是讨论、调查、规划、执行、修改计划还是反馈归档；区分日任务、周度项目和当日项目动作，不将周期项目默认为当天全部交付。
- 转换过程为“提取原意 → 核对已确认决策与必要资料 → 五项规格 → 歧义分流 → 按已有授权和本项目门禁执行 → 验收与交接”。不得只把原话换成术语。
- 将信息标为用户明确、已核实事实、AI 建议或待核实。无法从上下文确定的业务规则、项目对象、截止时间和预算不得编造；用户说“优化”“完成”时应转成可观察结果，含糊的关键取舍先问。
- 文件定位、现有方案和环境状态先只读查证；范围内可逆的实施细节由 AI 按项目惯例选择并说明。不能把可调查的信息全部退回给用户。
- 简单任务使用五项紧凑规格，持久任务写入已有任务记录；用户侧仅回述关键理解和需要决定的问题，不强制展示长表或让用户重填。已有任务修改原规格，保留变更原因。
- 涉及协作时，在同一 Task Spec 补充执行者、汇总者、依赖、输入输出、文件所有者、环境或工作树、验证及交接位置。能单任务完成时不强行拆分；提出分工不等于获准创建任务或启用并行。
- Task Spec 的技术建议不能产生授权。先检查当前用户指令及已有授权；不重复索取已覆盖的批准。本节不取消项目针对具体操作设置的门禁，也不自动授权外部发送、付费、部署或破坏性操作。
- 无法开始依赖关键未知的动作时，只问最小必要问题，并继续不依赖答案的安全调查。交付逐项对照验收，未知和未验证不能写成完成。
- 用户阅读材料：[项目任务协作指令手册](项目任务协作指令手册.md)。本节为模板增量，不自动更新已有项目；落地时按目标项目职责适配。

### 3.2 五项核心模板

> 2026-09-10 补充：执行 3.1 时同时适用下方 3.1a 自然语言转换规则。手册面向用户，机制面向 AI，两者独立。

```markdown
# Task Spec：<任务名称>

## 目标
- 用户想解决的问题、当前现象与预期结果；描述结果，不只列实现动作。

## 上下文
- 相关项目、文件、截图、错误、参考资料及其来源。
- 已核实事实、当前基线、必要前置条件与外部依赖。
- 未知项及其处理方式：待研究 / 待实验 / 允许 AI 提案 / 需要人工确认。

## 范围
- 本次允许修改或操作的对象及边界。
- 必须保持不变的内容、禁止触碰范围和明确不做的事项。
- 预期交付物及存放或呈现位置；只读任务明确无写入。

## 约束
- 必须遵守的业务规则、技术要求和不可破坏的不变量。
- 已明确的兼容性、性能、安全、环境、时间或成本限制；没有依据时不得自行设定硬指标。
- 关键取舍及其决定者；影响目标、范围、业务语义或验收的冲突须明确处理。

## 验收
- 逐项列出：前置条件 / 输入或操作 → 可观察的预期结果 → 验证方法与证据。
- 按任务风险覆盖正常路径、关键异常或边界路径，以及禁止出现的副作用。
- 区分 AI 可验证的项目与需要用户最终确认的项目；明确完成判据。
```

- 这五项是 Task Spec 的核心视图，与下文工程字段属于同一份规格，不另建重复事实源。
- 必须保留五项标题；确实不适用的细节注明“不适用”及简短原因。尚未核实的内容标记“未知”，不得以“不适用”掩盖信息缺口。
- 对可逆且不改变核心模型的实施细节，AI 可提出并注明默认选择；影响目标、权限、业务规则、不可逆操作或验收的关键未知必须先解决，不能当作已获授权。等待期间可继续独立的只读调查。
- 验收须与目标逐项对应，避免只写“优化完成”“体验良好”“测试通过”等不可独立判断的描述。

### 3.3 状态变更审批

所有会改变项目或外部状态的工作遵循：

`用户目标 / 需求依据 → Task Spec → 明确批准 → 受控实施 → 纵向验证 → 结果归档`

除只读调查与首错定位外，在当前 Task Spec 登记并获得用户明确批准前，不得修改业务代码、运行配置、数据库、部署目录或外部系统状态。

目标讨论、方向认可、历史授权、沉默或推定同意均不等于批准当前 Task Spec。没有批准证据时，状态只能是 `draft`。同一已批准 Spec 范围内的可回滚工作持续授权，无需为每个实施步骤重复审批；超出范围或触及需另行确认的边界时再处理。

涉及项目或外部状态变更时，应在五项核心之下补齐以下执行字段；只读任务按实际风险选用。字段不适用时说明原因，不得虚构代码映射、状态合同或回滚点：

1. 任务编号、用户目标、需求编号及权威依据。
2. 所属业务链或系统链、目标节点、预期结果和非目标。
3. 目标节点到真实代码结构的映射：仓库、模块、文件、类/函数/方法、配置键、入口、直接下游及架构节点 ID。
4. 上游输入合同、下游输出合同、状态字段及状态所有者。
5. 允许修改的文件、代码符号、状态读写集、外部副作用和数据变更。
6. 直接影响的相邻节点、必须保持不变的流程和禁止触碰范围。
7. 当前源码与运行基线、修改前快照或提交标识、回滚方案。
8. 最短真实纵向验证入口、预期结果、禁止副作用和完成证据。
9. 当前首错、实施顺序、停止条件、风险和下一门禁。
10. Spec 状态、展示时间、批准原话和批准时间。

上述字段的组织对应：目标承载 1—2 项，上下文承载 3—4 项及基线，范围承载 5—6 项，约束承载不变量、风险与停止条件，验收承载验证入口与完成证据；编号、实施顺序、回滚和批准记录可作为附录，避免重复维护。

- 另行明确阻塞性依赖及满足条件；有多项交付时标明先后顺序，必要时约定时间与资源预算。
- Spec 修订须记录版本和变更摘要，批准记录必须对应具体版本。审批与执行结果分开记录，不得把草案、已批准、实施中、受阻、待验收与已完成混为一谈。
- 交付时逐项对照验收标准，记录通过 / 未通过 / 未验证、证据、剩余问题及实际偏差；存在必需验收项未通过或未验证时，不得声称任务全部完成。

如果实施中发现真实首错或必要影响范围超出 Spec：

1. 立即停止超范围写入。
2. 保留现有证据并说明差异。
3. 将新增节点、文件、状态或副作用补入原 Spec。
4. 重新展示并取得明确批准后继续。

不得以顺手重构、测试便利或猜测影响为由横向扩大范围。

## 4. 精确实施边界

按系统建模工作流的 `PROJECT_MAP_VIEW_V1` 展示实际文件树、职责和依赖，初始化按 W04 建立最小地图。地图必须能导航到真实文件/符号和共享合同；新增、删除、移动、职责或依赖变化时更新。目录树不等于依赖图，文件路径不单独构成修改授权；分工前核对地图新鲜度及写入所有者。

文件级写集只是外层边界；真实实施边界必须精确到功能节点和代码符号。每个待修改节点应登记：

- 节点 ID、名称和职责；
- 正确输入、正确输出、失败出口和明确不承担的职责；
- 承载功能的文件路径及类、函数、方法或配置项；
- 读取和提交的状态、状态所有者及持久化位置；
- 直接上游、直接下游、外部接口和副作用出口；
- 本次允许修改的最小代码符号及允许影响的调用边；
- 同文件中不得修改的其他符号，以及同链中必须冻结的节点和流程。

若现有代码存在多层路由、职责混合或状态所有权不清，先通过只读追踪形成真实映射，再决定写入。映射未确认前不得修改代码。

写入共享文件前，应重新读取并合并并发变化。发现调用边、状态读写或副作用超出登记范围时，立即停止并修订 Spec。

## 5. 实施与验证规则

- 开发和修复优先遵循“最短真实纵向链 → 定位首错 → 只修首错 → 跑通后补充交付门禁”。项目特有细则放在 `<项目控制目录>/DEVELOPMENT_MODES.md`。
- 优先在唯一事实源或唯一修改现场完成变更，避免在本地、服务器或多个分支同时产生无法追踪的漂移。
- 项目已有架构登记时，Task Spec 引用现行节点与合同，不另造独立架构；新增功能通过既有节点或明确的扩展点接入，并说明关闭新增功能后原有主流程是否仍可运行。
- 工程验证不能代替用户最终业务验收。进程运行、健康码、HTTP 200、测试数量或单项单元测试通过，均不能单独证明业务目标完成。
- 验证应覆盖 Task Spec 约定的真实纵向链、状态账、错误路径、禁止副作用和回滚能力。
- 未验证的结果不得标记为完成。不能执行某项验证时，应明确标注“未验证”、原因、风险及用户可执行的验证步骤。
- 所有结论应附最小充分证据，例如测试结果、关键日志、状态快照、差异摘要或可复现步骤。

### 5.1 根因修复与防复发

执行标识：`ROOT_CAUSE_REPAIR_V1`。本节属于第 5 节实施验证的扩展；触发：缺陷修复、用户纠正、规则遗漏、重复失败或迁移偏差。普通任务先简短判断是否存在这类问题，不强制写长报告。

1. **界定问题**：记录实际现象、预期行为、影响与证据；先检查现有事实，不用“AI 疏忽”“提示不够清楚”替代原因。
2. **区分止损和修因**：必要时先恢复使用，但不能把局部补丁当根治。区分直接原因、产生错误的上游过程和未检出的验证缺口。
3. **追查到可干预环节**：沿输入、规则、生成/执行、验证、交接定位因果。用日志、版本差异、复现或文件对照支持结论；无法确认则标假设或根因未证实，不无限追问“为什么”。
4. **修复产生问题的机制**：在已授权范围内同时修当前产物及造成问题的源模板、映射、合同或校验。只检查直接同类产物，不借根因调查无限扩展重构；超范围处登记风险和下一步。
5. **验证两层结果**：原问题是否消失；相同触发条件或缺陷反例是否被阻止/检出。选择与问题相称的复现、场景演练、负例或回归检查，文档修复不硬套代码测试。
6. **判定与交接**：分别报告现象修复、根因置信度、机制修复及防复发验证状态。只补丁、只新增规则或未经运行的机制不能宣称永久解决；保留未验证项和恢复点。

最小记录格式：问题与证据 → 直接/上游/检出原因（事实或假设）→ 修复落点 → 原例与反例验证 → 剩余风险。记录到当前任务，不为每个小问题建立新文件。

#### 同根因扩展审查（ROOT_CAUSE_SWEEP_V1）

修 bug 不以眼前症状消失为终点。完成复现后，用证据建立“触发条件 → 错误假设或实现 → 失效结果”的因果链，同时检查上游产生环节与测试漏检原因；证据不足时保留假设和下一验证方法，不能把猜测包装成根因。

1. **提炼可搜索的错误模式**：例如同一不安全接口、复制的错误逻辑、共用模板/生成器、缺失的校验、相同状态更新或异步顺序假设。语法相似只是候选；判断其是否具有相同触发条件和失效路径。
2. **界定并执行扩展审查**：在当前项目内沿共享实现的调用方、同源生成物、复制实现与同类数据入口查找；记录搜索范围、方法、候选位置和因果关联。先看可复用的源头，再看下游；不因一个 bug 无边界扫描所有项目，也不只检查当前文件。
3. **逐项判定**：候选标为已确认同根因缺陷 / 有防护而排除 / 待核验，附最小依据。发现范围内的同根因缺陷与源头问题一并修复；超出已批准写集、涉及新业务规则或其他项目时，先完成只读审查，登记影响及待修订范围，不能静默扩写，也不能忽略发现。
4. **分层验证**：原问题修复前能复现、修复后通过；对已确认同根因位置验证相同触发条件；覆盖相关旧功能及必要边界。公共参数化检查可覆盖等价位置，需说明映射；不能用单点通过代表所有候选安全。改源模板后还须核对已生成内容，不假定自动修好。
5. **完整收尾**：分别报告症状、根因修复、扩展审查和回归验证状态。列已查范围、确认及排除项、未覆盖/待核验项、未修原因和恢复点。没有发现同类问题时也记录依据，只能说“在本次范围内未发现”，不能承诺全项目无 bug。存在必需未修/未验项时不得宣称整个修复闭环完成。

修复规格在同一任务增加：根因证据、错误模式、审查边界、候选判定、修复与验证映射；短任务可用简短段落，不要求用户填写或新增台账。K09 继承必须保留本节的扩展审查，不以只写“思考根因”替代。适用于四种 Task Spec 执行配置，未改变宿主权限或完成判定工具。

例：订单金额为零时被 `if not amount` 当作缺失。先核对业务是否允许零；确认后修正该校验，再审查使用相同校验函数、复制逻辑和生成模板的其他金额入口。对确实要求金额大于零的入口保留业务规则并说明排除依据；验证零、缺失及正常值，并保护已有订单流程。


## 5.2 执行验证合同（核心 K12）

执行标识：`EXECUTABLE_VERIFICATION_V1`。初始化/升级、修复、验证和收尾按 [执行验证细则](工作流库/执行验证.md) 绑定与调用 v0.2.0 执行器。AI 负责项目语义与检查选择，程序负责固定合同、实际执行、证据关联和完成判断。

- 项目配置绑定实际文件、所有者、需求、检查、环境/构建标识；初始化先预览，doctor 检查缺项。来源与执行器版本锁定；专用项目必须有可达本地路由与语义继承审阅，不能只留本源链接。
- 当前规格获批后冻结任务合同，真实执行 verify/finish；同范围不逐步骤重新审批。检查或业务标准变化显式说明差异，保留旧任务和证据。
- 回归检查证明能抓原缺陷，保护重要旧测试；必需失败/跳过/零测试/缺证据不能完成。证据关联源码、未跟踪文件、测试、配置和执行器，变化后保守失效。
- 人工项和工程检查分开；无可信人工确认时 pending_manual。ready 仅满足配置标准，不等于全部业务正确。
- W05 维护资料后重验；交付变化、结果、证据与局限。执行器未接入或无法运行应登记未完成/未验证，不能用手写 VERIFIED 替代。无软件项目采用领域断言，不创建无用 .env。
- 同权限本地程序不是安全隔离，不声称接管所有工具或自动理解规则；远程门禁与真实项目迁移另在明确授权下配置。

## 6. 协作、角色与节点

- 稳定的角色职责和通信方向只在 `<项目控制目录>/NODE_FUNCTIONS.md` 与 `<项目控制目录>/ROLES.md` 中维护。
- 未被明确指定为执行角色的协调窗口默认只负责汇总事实、维护任务指针和归档，不自动获得开发审批权。
- 讨论节点负责接收用户输入、形成 Task Spec 或单向执行指令；执行节点在批准范围内实施并回传必要增量。
- 复杂问题可创建短生命周期的诊断节点。诊断节点只做明确、可独立验收的子任务，返回精简证据后结束。
- 跨节点消息只传递任务指针、已确认事实和本轮必要增量，不复制完整历史污染上下文。
- 不把一次性故障、临时命令或未验证经验升级为项目根规则。可复用方法须经验证，并登记到对应专题协议。
- 长任务应持续提供简短、可见的进度更新：当前动作、已得结果、下一步、正在等待的对象及异常情况。

## 7. 归档与项目记忆

- 需求、Task Spec、架构决策、关键测试证据和最终结果应写入共享权威文件；聊天记录不作为唯一存档。
- 当前任务文件只保存恢复工作所需的最小状态：任务指针、阶段、所有者、基线、首错、写集、下一门禁和证据索引。
- 项目状态文件保存跨任务进度，不承载每次执行的流水账。
- W05 规定的状态、文件、接口、配置及规则变化，必须在同一任务内完成受影响资料的增量维护，不等用户另说“归档”。全量历史整理仍只在用户要求或项目工作流触发时进行；日常工作不广播、不轮询、不无限记录。
- 归档内容应区分：已验证事实、决策、假设、未决问题和后续行动。
- 发现新证据时，同步修正受影响的规则、模型和文档，保留必要的变更依据。

### 7.1 项目维护能力（核心 K11，必备 W05）

执行标识：`PROJECT_MAINTENANCE_V1`。源流程：[项目维护](工作流库/项目维护.md)。特异化时将适配后的流程写入项目自己的 AGENTS.md 或其引用的本地文件；不能把本源链接当作已完成绑定。

- 开始时按维护登记表读取本轮必要事实；用户需求或实施造成状态、文件、职责、依赖、接口、配置或维护规则变化时，识别关联记录，按已授权范围同步并核验。只读任务报告差异，不自行修复。
- 每个维护对象明确：实际路径/章节、唯一职责、读取触发、更新触发、写入所有者、更新动作、验证方式和证据位置。小项目允许合并文件；未触发的条件对象不建空壳。
- 当前状态作为可直接恢复的有效摘要维护；旧状态移入或标记为历史，保留来源、日期和必要变更依据。不能靠不断追加多个“最新状态”让接手者猜测，也不删除原计划或验证历史。
- 环境配置按 W05 条件流程维护变量名称、用途、加载与验证方法、示例及环境差异；真实凭证只走目标项目批准的存储机制。Codex 工具配置与业务程序配置分别管理，不为文档更新顺带修改全局配置。
- 每次有文件变更的交付报告增/改/删/移、原因与效果、结构/依赖/接口影响、关联资料同步情况、验证及下一步；无结构变化明确说明。无写入则如实报告；大变更可链接清单并概括关键影响。
- 维护流程自身变化也要检查入口、登记表、模板、调用它的工作流与继承清单；保存版本/原因，执行领域场景和缺项反例审阅。仅更新源框架不自动覆盖已存在项目。
- 必需维护尚未完成时分别报告业务结果与维护缺项、责任人和恢复点，不能宣称全部完成；无权写共享记录时交给其所有者，不越权、不制造另一份事实源。

- 允许智能体为容量管理自动压缩上下文。上下文压缩不等同于项目同步、归档、审批或任务交接。
- 不得仅为压缩上下文而暂停实施、重复讨论已定方案、编写冗长交接文或等待其他节点确认。
- 压缩后从当前首错或未完成动作继续。恢复事实时，只读取最小启动文件和本轮路由文件，不全量重读历史。
- 根 `AGENTS.md` 只维护启动入口、读取路由、通用门禁和绝对边界；详细流程、业务合同和环境资料放入项目控制目录，并由 `INDEX.md` 提供唯一入口。

## K04 格式增量：TASK_SPEC_MODES_V1

自然语言转规格时按需读取 [Task Spec 格式](TASKSPEC.md)，根据用户指定的单次、Goal、定时或 Heartbeat 填公共五项与对应配置。只整理不启动；实际启动依据宿主工具结果。用户未指定不静默开启 Goal。特异化必须将格式合并/复制到项目本地，根 AGENTS 引用唯一格式，K04 映射核对模式选择、授权、启动证据、暂停恢复及统一验收。格式变化同步地图和维护登记；不自动迁移旧项目。本增量保持 r6/v0.2.0 执行器合同，以来源提交 SHA 区分。
