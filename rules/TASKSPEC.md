# 按执行模式转换 Task Spec

格式版本：TASK_SPEC_MODES_V1（2026-09-10）。维护者：框架维护者；项目适配后由项目规则维护者负责。本文是格式唯一来源，AGENTS.md 只保留触发与路由。具体任务复用自己的规格，不复制四份。

## 转换规则

1. 提取用户原始需求与指定模式，核对当前任务、项目事实和授权。用户负责结果与关键取舍，AI 负责技术字段；保留用户原意，不增加目标。
2. 区分“只整理规格”和“开始执行”。只整理、先讨论、先给我看时，不启动目标或调度。已明确要求按某模式执行且范围清楚时，沿用授权，不因填写模板重复询问。
3. 用户未指定模式时，普通当前任务默认单次执行；可建议其他模式，但不得静默开启 Goal。明确的定时或回访请求按宿主规则映射，不要求用户使用英文术语。
4. 填写公共五项与选定配置。能调查的先调查；未知业务规则、时间、时区、预算等不编造。关键歧义先澄清，可继续不依赖答案的工作。
5. 规格确认与启动成功分开。读取当前宿主工具定义，调用真实机制后核验返回状态；工具缺失、拒绝或结果不明时，记录未启动、启动失败或待核验，不能暗中降级后声称原模式已启动。
6. 统一执行与验收：单次也应持续完成本轮已授权工作，不以“没有 Goal”为提前结束理由；中断、暂停、待验收不等于完成。保存证据、剩余范围和恢复点。

## 公共格式

```text
目标：可观察的最终结果。
上下文：用户原始需求、已确认决策、查证事实和资料引用。
范围：交付对象、可写边界、非目标及需要保护的已有行为。
约束：授权边界、依赖、关键未知、必要暂停条件。
验收：每项结果的检查方法、证据与必要人工判断。

执行配置：从以下四项选择；只填相关字段。
规格状态：草案 / 已确认；附对应用户请求或批准依据。
执行意图：仅整理 / 执行。
实际启动状态：未启动 / 已启动 / 启动失败 / 待核验 / 不适用。
启动证据：真实工具返回的标识、状态、核验时间；没有则写无。
任务进度：未开始 / 执行中 / 暂停 / 阻塞 / 待验收 / 完成。
恢复点：已完成、剩余、下一步及证据位置。
```

启动证据属于运行记录；检查器冻结的规格/检查标准不要为记录启动状态而反复改写。沿用项目现有运行记录关联同一任务；若目标或标准改变，显式修订并按执行器规则重新捕获合同。

## 四种执行配置

### 单次执行

```text
模式：单次执行
本轮交付边界：本轮应完整交付的结果。
实施顺序：必要步骤与依赖，可随证据在范围内调整。
结束条件：满足本轮验收；或真实阻塞/用户暂停并留下恢复点。
实际启动状态：不适用（无独立模式开关）；任务进度按实际记录。
```

例：“这次把预约时间选择修好，已有订单不能坏。”→ 核对复现与相关文件，限定修复范围，验证预约选择及已有订单回归；不能做完一半就把剩余工作当作可选后续。

### Goal 持续执行

```text
模式：Goal 持续执行
总完成标准：目标全部达成的可验证条件。
阶段与自主范围：各阶段结果、依赖、允许自行决定的细节。
暂停与恢复：真实阻塞、用户决定、权限或外部条件；恢复依据。
预算：仅记录用户明确指定的预算；未指定不擅设工具预算。
宿主机制：当前可用的目标创建、状态查询和结束工具及限制。
```

例：“用 Goal 模式把预约流程做到可以验收，支付先不做。”→ 把预约流程转为有边界的总目标与阶段验收，按明确请求启动 Goal，并保存实际结果。只说“整理成 Goal 规格，先给我看”仍保持未启动。

Goal 必须有用户明确请求；“持续做到完成”不自动等同于启用 Goal。已有活动目标时先查询，沿用相关目标或澄清冲突，不能虚假结束旧目标来创建新目标。完成、阻塞的工具操作遵守当前宿主条件，不能仅凭模板状态强制结束。

### 定时执行

```text
模式：定时执行
时间规则：日期或频率、时区；必要时明确截止日期。
每次运行：输入、工作范围、单次验收与失败处理。
重复处理：已处理记录、去重依据、补跑规则。
通知：何种结果需要通知；沿用用户偏好。
生命周期：暂停、修改、结束条件与实际调度标识。
宿主映射：实际使用的自动化类型和目标任务/项目。
```

例：“每天早上九点收集这个项目的新问题。”→ 核对时区、问题来源和去重依据，再创建或更新实际自动化并核验。先查相同调度，避免重复创建；不将“每天”只写进文档当作已安排。

### Heartbeat 回访

```text
模式：Heartbeat 回访
跟进对象：明确任务、状态或外部条件。
检查间隔：用户指定或明确标为建议的间隔。
变化判定：什么证据算有进展、异常或已满足条件。
继续动作：每次允许做的检查与后续行动边界。
通知与停止：有意义变化才通知；何时结束或暂停回访。
宿主映射：实际回访机制、任务关联与调度标识。
```

例：“持续关注构建，失败时告诉我。”→ 确定构建对象、查询方式、频率、失败通知和终止条件；无变化默认安静。监测授权不自动授权修代码、重发部署或联系其他人。

## 组合与宿主适配

四项是用户常用表达，不是互斥的四个软件按钮。Goal 描述持续推进，定时/回访描述何时运行；明确要求组合时，在同一任务记录触发配置和执行配置，避免每次唤醒重复创建 Goal。

用户切换模式时修订同一规格，保留原模式和启动记录；先核对旧目标/调度实际状态，明确继续、暂停或结束的处理。按切换授权与宿主能力处理并核验，不静默留下会继续执行的旧调度，也不擅自删除无关调度。缺少必要授权或停止能力时披露待处理项。

在当前 Codex 宿主，重复请求按可用自动化工具规则默认映射为当前任务的 heartbeat；用户明确要求每次独立任务或独立项目作业时才使用适用的 cron。以当次工具定义为准，不从本格式硬编码所有客户端行为。未提供这些机制的宿主仍可生成规格，但须说明尚不能启动相应机制。

## 继承与验收

修 bug 时，四种模式均按 目标本地 AGENTS 的 K09 同根因扩展审查 补充同一规格的根因证据、错误模式、审查边界、候选判定及修复/验证映射。AI 负责调查与填写，不要求用户额外说“检查同类问题”。

初始化或升级时，把本文适配到目标项目的本地文件（如 `.project/TASKSPEC.md`），从目标 AGENTS.md 明确引用；已有同职责文件则合并，不建立重复来源。K04 映射必须包含该实际路径、模式转换及启动核验，文件地图登记职责和维护者。源码升级不自动覆盖已有项目。

四种方式共同遵守当前项目的验收门禁：必需测试未运行、失败、缺证据、证据过期或必要人工项未确认，都不能标全部完成。jxcheck 不创建 Goal 或自动化，也不验证用户是否真正指定某模式；本文件是 AI 转换与宿主调用规范，不是新增调度器。

语义审阅至少检查：四种自然语言正例；只生成不启动；未指定不启用 Goal；工具不可用不假报；已有调度不重复；模式切换保留历史且不静默遗留旧调度；缺验收不能完成。结构/夹具检查不等于新会话行为实测。

四种模式的验收部分均依目标本地 K06/K12 验证流程建立需求场景与检查映射，保存关键断言的故障检出证据及最终交付版本结果。规格描述检查要求，真实执行证据在运行记录；不把定义测试当已运行。
