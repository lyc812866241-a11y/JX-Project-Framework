# 发布回滚

类别：基础必选。
用途与触发：执行发布、部署、数据迁移或恢复时使用。无发布场景的项目，在专用框架注明当前不适用即可，不创建部署文件。纳入规则不代表获得发布授权。
必要输入：精确目标、实际版本与环境、适用授权、验证入口、恢复点及停止条件。

## 步骤

1. 核对目标和现状，区分源码版本、构建产物与实际运行版本；不假设三者一致。不编造命令或环境信息，不记录真实密钥。
2. 在修改前确定恢复方式：代码、配置、数据和外部副作用分别考虑。Git 回退不能代替数据库恢复；无法恢复的部分明确说明，并按项目规则处理。
3. 在授权范围内执行已核对的发布或迁移步骤，保留必要操作证据；触及停止条件时停止后续操作。
4. 从真实入口验证发布结果、相关状态和禁止副作用，并核对实际运行版本。验证失败时，根据预定条件和授权执行恢复，不能把“准备了回滚方案”写成“已回滚”。
5. 恢复后再次验证实际状态。若曾直接修补服务器产物，补齐正式源码中的对应修改与验证；尚未完成则留下明确待办。
6. 按 [项目维护 W05](项目维护.md) 更新实际基线、当前状态、环境说明及本次受影响的接口/地图。发布失败或回滚后不得保留旧的成功状态为当前结论；保留发布前和恢复证据，并报告尚未同步项。

## 产出与验证

优先使用项目已有发布或任务记录；确有发布需求且无合适记录时，再创建项目内专用文件并建立路由。
填写目标、版本、实际命令、配置或数据变化、恢复点、停止条件、验证结果与未完成项。保留发布前基线，避免只更新当前版本而丢失恢复依据。
完成标准：实际结果有证据，源码、产物与运行状态关系明确；恢复若已执行，必须有恢复后的检查结果。不能验证时标记未验证。

来源：旧启动模板 WORKFLOWS.md、DEVELOPMENT_MODES.md 与 .project-baseline/README.md；已提炼，尚未在新项目验证。

## r5 完成证据边界

发布或恢复后按 [执行验证](执行验证.md) 验证实际环境/构建标识及登记的真实入口；本地 ready 不等于部署成功。来源/环境无法绑定时保留未验证。框架文件安装恢复只处理受管文件，不能代替数据库或外部副作用恢复。
