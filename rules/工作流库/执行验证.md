# 执行验证

类别：K12 的执行细则，由必备 W04/W02/W05 路由；不是每轮额外全量流程。版本：2026-09-10-v1；执行器 v0.2.0。

## 触发与输入

初始化/升级具体项目时绑定；产生可验收交付、修复回归、检查定义或源码变化时执行。输入：目标实际规则、已批准 Task Spec、读写范围、需求与重要不变量、运行条件、适配本领域的检查与人工项。

规则与检查器是两层：AI 负责按项目语境选择标准和维护资料，程序校验合同并采集执行证据。不能将程序结构检查等同于语义继承或业务正确性。

## 流程

### 先建立需求测试集（REQUIREMENT_TEST_VALIDITY_V1）

本节为测试集设计的唯一流程来源，属于 K06/K12；初始化、需求变化、缺陷修复或发现漏检时按影响范围执行，四种 Task Spec 模式共同适用。AI 负责调查、设计和运行，不把已明确路径的基础测试转交用户。用户确认关键业务取舍和产品体验；可从需求与资料确定的预期不逐条重复询问。

1. **从需求推导路径**：先读原始需求、已确认业务规则及真实使用入口，再检查实现。识别正常路径、重要状态变化和适用的失败/边界情形；持久保存、身份隔离、刷新/重启恢复、重复操作、网络失败、并发等按实际风险选择，不给所有项目机械套全套。未知预期标待确认，不能从当前代码行为倒推正确答案。
2. **登记可执行场景**：复用现有测试计划或当前 Task Spec 的验收部分，以稳定场景 ID 关联需求、前置数据与身份、环境/设备/依赖版本、输入与操作、逐步可观察预期、最终状态断言、检查 ID 和证据位置。注明真实服务/模拟服务边界及未覆盖范围。场景存在不代表已自动化或已执行。
3. **检查断言质量**：必须验证用户要求的真实结果；点击成功、按钮变色、HTTP 200 或成功提示不独立证明数据保存。按目标检查重新读取、重新登录、输出内容、状态一致性或禁止副作用；优先通过对外行为取证，必要时补查授权测试数据。测试期望依据需求，不与实现共用可能出错的计算逻辑。
4. **证明关键测试有效**：针对本轮新增/修改的关键断言、修复回归及已暴露的漏检，在隔离副本/测试环境关闭目标行为、注入代表性故障或复现旧缺陷，确认指定断言因预期缺陷失败，而不是依赖缺失、语法错误等无关原因。保留正常通过→故障被检出→恢复后通过的证据和场景映射。共享机制可用代表样本并说明覆盖边界；不要求每轮全量变异测试。不改生产数据、不提交故障注入版本；无法安全执行时记录未验证原因，不能宣称测试有效性已验证。
5. **实际运行并修复**：将场景接到 project.json 的需求/检查合同，在已授权环境实际执行。失败按 K09 复现、根因修复和同根因审查处理；修复后复跑相关场景及受影响旧功能。缺工具/环境时记录阻塞或未验证，不用模拟结果冒充真实路径。随机、并发或时序场景明确种子/调度条件、重复次数与判据，不以重试到一次成功隐藏失败。
6. **复验交付版本**：证据关联最终源码、测试、配置及实际运行构建；检查后改变这些输入需按当前合同重新验证。若交付包含部署，在授权部署后核验实际运行产物/版本及关键真实路径；仅本地通过不能报告线上通过。外部服务、设备、依赖与数据状态另外登记，源码摘要不证明环境相同。
7. **持续补齐测试集**：用户在已约定路径发现问题时，区分漏场景、断言错误、环境差异、版本不符、未执行或时序不稳定，保存证据并修正测试和上游生成/审查机制。新增覆盖、改变预期、删除/放宽保护项分别记录；不得为过关降低标准。合同变化按原执行器规则建立新修订并保留旧证据。

最小场景记录可为一行：`场景ID → 需求依据 → 前置条件/环境 → 操作 → 预期与断言 → 检查ID → 有效性证据 → 最终版本结果/缺口`。使用已有任务/测试计划，避免第二套独立事实源；保存位置、维护者及读取触发登记到项目地图/维护流程。每轮交付分别说明场景设计、自动化、实际运行、有效性验证及业务验收状态，不能混为一个“全部通过”。

例：需求为“地址保存后仍可使用”。路径为填写→保存→离开→重新进入→地址内容正确；若需求要求跨登录保存，则增加重新登录后的读取。隔离环境让保存只更新界面、不持久化，重新进入断言必须失败。只有“保存成功”提示的检查不能验收持久化。账号隔离若适用，另设不同账号不能读取该地址的场景。

必需场景未自动化但已按同一条件实际手动执行，应如实标手动证据；未运行、失败、缺证据及必需有效性验证未完成不能报告完整验收。jxcheck 只执行配置与核对证据，不自动证明测试集合完整、语义正确或全部故障已覆盖。未编码为检查的语义项由 AI 明确审阅并保留缺口，不能把 ready 当作额外的语义保证。

特异化时把本流程适配到项目可达的本地验证文件，从根 AGENTS 路由，K06/K12 映射保留路径设计、断言、故障检出、真实执行和交付复验。无软件领域按实际产物采用来源/内容/状态验证，不虚构浏览器或数据库测试。

### 执行器绑定与运行

1. 按 W04/W05 复用本地文件和维护者；在 `.project/project.json` 绑定实际路径、需求 ID、检查 ID、可观察期望、必需性、所有者、步骤、证据、参数数组/cwd 和非敏感环境/构建标识。文件名按领域适配。
2. 准备项目专用 manifest，init/upgrade 先预览；按已有授权应用。冲突保留用户内容，不复制旧个人权限。锁定规则/执行器来源和摘要，运行 doctor，语义继承另做场景审阅。CLI 只做绑定安装，不替代完整项目初始化或 Git 规则。
3. 当前 Task Spec 获批后，用 task 命令冻结检查合同、规格和写集基线。简单已批准工作不逐步骤再确认；首次变更合同、扩大范围或外部副作用按原边界处理。不能把 CLI 捕获命令当用户身份认证。
4. 修复先保存原缺陷复现或在隔离副本跑出失败；新增针对性回归，保留重要旧流程。JUnit 配置受保护测试名，测试意义/期望变化另审，不能静默删除或放宽。
5. verify 运行登记的命令或领域断言，采集结构化报告/截图。必需失败、跳过、零测试、错误、缺附件不能通过；源码/测试/配置/未跟踪文件变化后保守重跑。不支持报告格式明确待适配。
6. W05 同步受影响状态、地图、接口、环境和维护流程后，重新 verify、finish，避免同步文档后继续使用旧证据。范围外变化先解释并处理，不能直接扩大通配符掩盖。
7. finish 返回 ready/pending_manual/blocked/stale。人工项缺可信确认来源则保留待人工验收；ready 只代表配置标准满足。结果附证据路径、实际覆盖、变化与恢复点。

## 维护与边界

执行器/规则升级先看差异、保存旧包与文件恢复点；重审继承与正常/负例。项目接入登记区分已绑定、本地实测、远程门禁实测。源升级不自动传播旧项目。

本地同权限可绕过；没有宿主 Hook、身份认证或远程保护时明确写明。密钥不放参数/报告；秘密环境与外部服务变化需项目补充验证，不由哈希推断。无软件领域采用文件/状态/来源检查及人工项，不强制 .env 或软件测试。

实际命令和字段：[执行包说明](../../README.md)、[合同](../../CONTRACT.md)、[恢复](../../UPGRADE.md)。在专用项目落地时转换为项目可达的本地路径，不依赖 JX 的个人绝对路径。

## 最低验收

正常检查可完成；原缺陷回归能失败；检查定义改变/必需跳过/零测试/证据替换/检查后改源码不能完成；无人工凭证不冒充通过。至少一条真实项目入口验证后才登记本地实测。包内隔离样例不是所有业务项目接入证明。
